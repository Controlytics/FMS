A System Request Flow

Every call travels the same rail: the SPA sends a Bearer JWT (plus an x-reauth-password header on sensitive actions); Fastify runs three gates in order before any handler; the handler reads/writes Postgres and always writes a hash-chained audit row. Background crons run in an in-process graphile-worker runner.

The models behind these subsystems in apps/api/prisma/schema.prisma. Note the two link styles: hard FKs (solid crow's-foot, ON DELETE CASCADE) vs DigiLog's soft links — User.role→Role.name by string, and several userId columns that reference users.id by convention with no database FK (dashed lines). Why soft links matter. Because roles are joined by name and the audit actor is a plain varchar, deleting a role or user does not cascade to config rows or rewrite history — audit_trail keeps the original actor id forever (21 CFR §11.10(e)), and the hash chain is never touched by identity changes. Backups strip password_hash from USER and PASSWORD_HISTORY to a sentinel and re-apply on restore.

2 Audit Trail — Tamper-Evident Hash Chain

4 Re-authentication Flow

Sensitive actions require a fresh password re-verification (21 CFR §11.200). The action-reauth config stores a { ACTION: [roles…] } map. This deployment has re-auth ON (~80/82 actions, no SA bypass on config).

Figure 4 — Re-auth shares the same lockout accounting as login, so it is not a non-locking brute-force oracle.

Config-shape defense. normalizeActionReauthConfig rejects a legacy nested shape (returns {} and warns) — a malformed save turns re-auth off loudly rather than silently mis-gating. Cache TTL 10s; config at /config/action-reauth (SUPER_ADMIN).

8 Electronic Signatures

There is no ElectronicSignature model (dropped 2026-07-04). A compliant e-signature is assembled from three live parts: (a) re-authentication (password re-verify) as the signing act, (b) the signatureMeaning field written into the hash-chained audit row as the signing intent, and (c) the ReportReview submit→review→approve workflow that carries the signer identity + timestamp on the record itself.

RequirementHow metVerdict
§11.200 unique to one individual / two componentsUsername + password re-verified at each act; session (req.user.sub) ties it to the loginPartial only password re-presented at sign time; session is the 2nd component

Compliance gaps to flag. (1) No cryptographic per-user signing key / PKI — signing is a password comparison against a stored bcrypt hash; there is no artifact only the signer could produce. (2) signatureMeaning is invisible in the web UI (0 references in apps/web/src) — a §11.50 display gap. (3) Stage‑1 “Printed By” is not reauth-signed — only review & approve require a password. (4) PDF prints the print timestamp, not the sign timestamp, and omits the meaning string.
