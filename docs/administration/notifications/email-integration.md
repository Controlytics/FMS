# Email Integration Guide

> DigiLog email notification delivery via Office365 SMTP with OAuth2 or Basic Auth.

---

## Overview

DigiLog sends email notifications for 14 event types (alarms, device status, user activity, rule chains, checklists, system errors) through configurable notification rules. Emails are sent via SMTP using Nodemailer with support for Microsoft Office365 OAuth2 authentication.

---

## Configuration

Email settings are stored in the `system_config` table under the key `notification-email`.

### Access
- **UI**: Notifications > Email Settings (SUPER_ADMIN only)
- **API**: `GET/PUT /api/notification-settings/email`

### Auth Types

#### OAuth2 (Recommended for Office365)

| Field | Description | Example |
|-------|-------------|---------|
| `authType` | Must be `oauth2` | `oauth2` |
| `oauth2Provider` | OAuth2 provider | `microsoft` |
| `clientId` | Azure AD App Registration client ID | `f054d230-e213-...` |
| `clientSecret` | Azure AD App Registration client secret | `4Ct8Q~Zwn...` |
| `providerTenantId` | Azure AD tenant ID | `25eab698-fe9f-...` |
| `refreshToken` | OAuth2 refresh token (obtained via callback) | `1.AcYAmL...` |
| `accessToken` | Auto-managed by the system | _(auto)_ |
| `tokenExpiresAt` | Auto-managed token expiry timestamp | _(auto)_ |

**Setup Steps:**
1. Register an app in Azure AD with `SMTP.Send` permission
2. Configure redirect URI for OAuth2 callback
3. In DigiLog email settings, enter clientId, clientSecret, tenantId
4. Click "Authorize" to complete OAuth2 flow and obtain tokens

#### Basic Auth

| Field | Description | Example |
|-------|-------------|---------|
| `authType` | Must be `basic` | `basic` |
| `username` | SMTP username (email) | `user@company.com` |
| `password` | SMTP password or app password | `AppPassword123` |

> **Note:** Microsoft requires "app passwords" if MFA is enabled. Regular passwords will fail with "Authentication unsuccessful".

### SMTP Settings

| Field | Default | Description |
|-------|---------|-------------|
| `host` | `smtp.office365.com` | SMTP server |
| `port` | `587` | SMTP port (STARTTLS) |
| `secure` | `false` | Must be `false` for port 587 (STARTTLS) |
| `fromEmail` | _(required)_ | Sender email address |
| `fromName` | _(optional)_ | Sender display name |
| `connectionTimeout` | `10000` | Connection timeout in ms |
| `socketTimeout` | `15000` | Socket timeout in ms |

## Templates

### Database Templates

Templates are stored in the `notification_templates` table with `channel = 'EMAIL'`.

| Template | Variables | Description |
|----------|-----------|-------------|
| **All Events (Combined)** | `eventLabel`, `summary`, `details` | Universal template - auto-adapts per event type |
| Per-event defaults | Event-specific | 14 built-in fallback templates |

### Template Variables

- `${eventLabel}` — Human-readable event name (e.g., "Alarm Created", "User Login")
- `${summary}` — Brief summary (alarm type, username, device name, etc.)
- `${details}` — HTML table with event-specific fields (auto-generated by dispatcher)

### How Dynamic Details Work

The notification dispatcher builds the `${details}` variable dynamically based on event type:

```
ALARM_CREATED → Shows: Alarm Type, Severity, Entity, UNS Path, Trigger Condition, Alarm ID, Time
USER_LOGIN    → Shows: Username, Full Name, Role, IP Address, Time
DEVICE_OFFLINE → Shows: Device, UNS Path, Time
```

Only fields with actual values are included — no empty rows.

## Technical Details

### Code Path
- **Email Channel**: `apps/api/src/modules/notification-delivery/channels/email-channel.ts`
- **Dispatcher**: `apps/api/src/modules/notification-delivery/notification-dispatcher.ts`
- **Config Loader**: `apps/api/src/modules/notification-delivery/config-loader.ts`
- **Delivery Service**: `apps/api/src/modules/notification-delivery/delivery.service.ts`

### IPv4 DNS Workaround
EC2 instances may resolve `smtp.office365.com` to IPv6 addresses which are unreachable. The email channel uses a custom DNS lookup function that forces IPv4 resolution:

```typescript
const ipv4Lookup = (hostname, options, callback) => {
  dns.lookup(hostname, { ...options, family: 4 }, callback);
};
```

### Retry Logic
- Failed emails are retried up to **3 times** with exponential backoff
- Each attempt is logged in the `notification_logs` table
- Final status: `SENT` or `FAILED` with `error_message`

### OAuth2 Token Refresh
- Access tokens expire after ~1 hour
- System automatically refreshes using the stored `refreshToken`
- New access token and expiry are saved back to config

## Troubleshooting

| Issue | Cause | Solution |
|-------|-------|----------|
| "Authentication unsuccessful" | Wrong authType or bad password | Set `authType` to `oauth2` if using OAuth2 tokens |
| ENETUNREACH | IPv6 resolution on EC2 | Already handled by ipv4Lookup |
| "Token expired" | OAuth2 token stale | System auto-refreshes; if fails, re-authorize |
| Retrying in notification logs | SMTP error | Check `error_message` in `notification_logs` table |
| Email not received | Spam filter | Check spam/junk folder; verify fromEmail matches Azure AD app |

### Check Delivery Logs

```sql
SELECT status, error_message, recipient, created_at
FROM notification_logs
WHERE channel = 'EMAIL'
ORDER BY created_at DESC
LIMIT 10;
```
